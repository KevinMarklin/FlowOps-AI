# Защита ядра FlowOps AI

Дата: 23 ноября 2026. Проверенная версия: `c05c271`.

## Уточнённая область

После уточнения пользователя предмет проверки — сам сервис обработки обращений:

- приём из email, Telegram/MAX и API интеграций;
- анализ текста, защита от prompt injection, выбор и вызов LLM;
- маскирование данных и минимизация отправляемого провайдерам;
- выбор и изменение регламентов;
- сохранение обращений, серверная отправка ответов и callbacks;
- ограничения ресурсов и восстановление при ошибках внешних зависимостей.

Демо-сайт, его история заявок/метрики и пользовательские web-сценарии исключены. Настройка корпоративной сети, SSO, reverse proxy, инфраструктуры PostgreSQL, контейнеров и юридическая оценка также не являются задачами этой проверки. Их отсутствие не используется здесь как самостоятельный дефект сервиса. HTTP API интеграций, исходящие HTTP/SMTP-запросы и код авторизации сервисных операций остаются частью серверного контура.

Предположение: реальный вход — workers и `/api/v1/ingest`; демо-эндпоинты создания web-заявок и пользовательской обратной связи не будут частью рабочего контура. Если последние всё же будут опубликованы как рабочие API, их серверные проблемы из первоначального отчёта снова применимы.

Это уточнённый отчёт для дальнейшей работы. `security_best_practices_report.md` и `FlowOps-AI-threat-model.md` отражают первоначальную, более широкую область; их выводы о демо-интерфейсе и окружении не являются текущим списком задач. Аудит не вносил исправлений runtime-кода.

## Порядок доработки

1. **Передача данных моделям.** Исключить sender из модельного payload. Ввести явный список разрешённых провайдеров/режимов и правило fallback для чувствительных данных. Устранить конкретные пропуски маскирования; не объявлять regex универсальным доказательством обезличивания. Для данных, которые нельзя передавать, использовать локальный маршрут или явный отказ до сетевого вызова.
2. **Исходящие запросы.** Закрыть произвольные callbacks: зарегистрированные доверенные назначения, проверка URL и адреса соединения, запрет redirects. Включить обязательную проверку TLS в MAX; запретить отправку секретов на незашифрованный endpoint. Добавить deadlines для полного почтового сеанса.
3. **Вход интеграций.** Отдельные credentials/подпись для ingest, защита от повторов, серверное определение доверенного канала и привязка адресата. Это сервисная аутентификация; переделка демо-сайта для неё не нужна.
4. **Ресурсы и доставка.** Ограничения до хранения, отдельный бюджет внешних моделей и доступная локальная обработка, ограниченная очередь отправок. Транзакционный outbox с повтором и idempotency, отдельное состояние доставки.
5. **Зависимости и регламенты.** Совместимые security updates с повторным scanner и тестами; подтверждение публикации KB и проверяемая аудитория. Доступ к файлам/системам за пределами процесса в задачу не добавляется.

## Что сохранено из существующей защиты

LLM не получает KB и не имеет инструментов. Ответ классификации проверяется по JSON-контракту; модельный текст решения не используется. Провайдерские redirects запрещены, body/time caps есть. Обновление KB валидируется до замены файла. Эти свойства относятся именно к сервисному ядру и сохраняют значение независимо от демо-интерфейса.

## Доказательства и границы результата

Обычные Go-тесты, go vet и локальные proof-тесты выполнены. Доказательства — `reports/security-audit-2026-11-23/proofs/`, `proof-results.txt`, `unit-tests.txt`, `coverage.out`. Проверки callback/TLS/masking использовали синтетические данные и loopback, без внешних сообщений и рабочей БД. Старые proof-тесты web/middleware остаются историческими материалами и не расширяют текущую область.

Для каждой будущей доработки требуются отрицательные проверки: sender отсутствует в payload; запретный provider не вызывается даже при ошибке основного; неизвестный callback/redirect/private address отклонён; неверный сертификат не получает токен; неавторизованный ingest не запускает анализ/доставку; исчерпанный LLM-бюджет не выключает безопасную локальную обработку; ошибка отправки не теряет событие.

Отсутствие ошибок во всём сервисе не доказано. Промышленную готовность ядра можно оценивать после исправлений и тестов реального pipeline на изолированном стенде; состояние демо-сайта не является критерием допуска ядра.
