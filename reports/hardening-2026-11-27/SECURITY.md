# Проверка и исправления безопасности — 27 ноября 2026

## Границы проверки

Проверены Go HTTP API, авторизация сотрудников, подтверждение регламентов,
ошибки внешних каналов, регистрация и время ответа сервера. Проверка основана
на коде и регрессионных тестах с искусственными данными. Она не является
подтверждением юридического соответствия 152-ФЗ и не исключает неизвестных ошибок.

База проверок: `flowops_security_test`, отдельная временная схема каждого теста.
Рабочие обращения, учётные записи и реальные внешние получатели не использовались.
Этот подпроцесс не выполнял коммит, push или развёртывание.

## Исправлено

### SEC-01. Неправомерное изменение статуса через HTTP feedback — средний риск

**До:** `TicketsHandler.Feedback` безусловно менял статус заявки по ID и компании.
Сотрудник мог закрыть собственную заявку без регламента либо изменить уже закрытую
заявку с ответом оператора; прямой вызов обработчика также не проверял владельца.
HTTP поведение расходилось с более строгими кнопками Telegram.

**Изменено:** [tickets.go](../../internal/handlers/tickets.go), функция Feedback,
строка 196 и далее: транзакция и блокировка строки `FOR UPDATE`, повторная проверка
владельца и компании в запросе, разрешение перехода только из
`awaiting_confirmation` с непустым регламентом и без ответа оператора. Одинаковое
решение принимается повторно только при существующем событии аудита; противоположное
устаревшее решение получает 409. Смена статуса и `TICKET_FEEDBACK` записываются
атомарно. Ошибка аудита откатывает статус.

**Доказательство:** новый `TestHTTPFeedbackRejectsInvalidStatesAndForeignOwners`
до исправления воспроизводил 200 вместо 409/404 и изменение недопустимых заявок.
После исправления проходит, включая одновременные противоположные решения,
единственное событие аудита и откат при ошибке аудита.

### SEC-02. Токен Telegram в сохранённых сетевых ошибках — средний риск

**До:** `net/http` включает адрес `/bot<TOKEN>/getUpdates` в ошибку соединения.
`channelStatusUpdate` сохранял её в `app_settings.channel_metadata`, а API настроек
возвращал `last_error` администратору. Это нарушало обещание не возвращать секреты
при чтении настроек и создавало дополнительные копии ключа в диагностике/БД.

**Изменено:**

- [prompt.go](../../internal/security/prompt.go), строки 39–47: `SafeLogError`
  удаляет credential из пути Telegram Bot API, сохраняя техническую причину.
- Новый [channel_errors.go](../../internal/security/channel_errors.go): единая
  очистка сообщений каналов и ранее записанных ошибок. Обновление старой ошибки
  сравнивает исходное значение, не перезаписывая более свежий статус обработчика.
- [main.go](../../cmd/server/main.go), строка 116: очистка до сохранения metadata.
- [integrations.go](../../internal/handlers/integrations.go), строка 321:
  дополнительная очистка `last_error` перед ответом API.
- [db.go](../../internal/database/db.go), строка 186: существующие ошибки очищаются
  при миграции/запуске; имена и идентификаторы подключённых ботов сохраняются.

**Доказательство:** `TestChannelErrorRedactsTelegramURLCredential` воспроизводил
утечку искусственного canary-токена до исправления и проходит после него.
`TestChannelMetadataHidesAndMigratesOldTelegramTokens` проверяет ответ API и
очистку ранее сохранённого токена при повторном запуске миграции.

### SEC-03. Неограниченное накопление IP в регистрации — низкий риск

**До:** публичная регистрация компаний сохраняла запись для каждого IP навсегда.

**Изменено:** [operator.go](../../internal/security/operator.go), строка 163:
истёкшие минутные окна удаляются; максимум 10 000 записей; десять регистраций
с одного IP за минуту; при отказе возвращается `Retry-After: 60`.

**Доказательство:** `TestWorkspaceRegistrationLimiterExpiresAndCapsIPs`
проверяет лимит, возобновление после истечения минуты и освобождение памяти.

### REL-01. HTTP ответ мог оборваться раньше модели — риск надёжности

**До:** WriteTimeout HTTP сервера составлял 10 секунд, тайм-аут клиента ИИ —
15 секунд. Поэтому медленный анализ мог завершиться сохранением заявки после
потери клиентом ответа и привести к повторной отправке пользователем.

**Изменено:** [main.go](../../cmd/server/main.go), строка 245: WriteTimeout
увеличен до 45 секунд. ReadHeaderTimeout, ReadTimeout и IdleTimeout сохранены.
Это даёт запас для текущего единственного провайдера Алисы, но не заменяет
идемпотентность создания заявки и не гарантирует поведение при медленной БД.

### SEC-04. Неограниченный размер списка заявок — средний риск доступности

**До:** `TicketsHandler.List` возвращал все обращения компании/сотрудника,
включая исходный текст и ответы. Частые запросы масштабировали расход БД, памяти
и трафика вместе со всей накопленной историей.

**Изменено:** `internal/handlers/tickets.go`, List: keyset `before_id`,
`limit` по умолчанию 100, максимум 200. Повторные, отрицательные и неверные
параметры возвращают 400. Сортировка `id DESC`, ограничение `LIMIT limit+1`,
в ответе остаётся массив; `X-Next-Cursor` содержит ID последнего показанного
элемента только при наличии следующей страницы. Проверки владельца и компании
остаются в SQL. Добавлены индексы `(tenant_id,id DESC)` и
`(tenant_id,requester_id,id DESC)` в миграцию и schema.sql.

**Доказательство:** `TestTicketListPaginationBoundsAndOwnership` на 205 личных
и двух чужих заявках с намеренно различающимся `created_at` воспроизводил
неограниченный ответ до исправления; после проверяет limit/cursor/валидацию,
отсутствие повторов и потерь, сохранение изоляции владельца и компании.

## Оставшиеся ограничения и приоритеты

1. Нет сквозной идемпотентности создания обращений по Telegram message/update ID
   и HTTP ключу запроса. Повторная доставка после сбоя или повтор пользователя
   может создать дубликат. Увеличенный WriteTimeout решает только один триггер.
2. Группы MAX теперь блокируются на приёме заявок и доставке ответов. Состав
   и условия обработки личных каналов всё равно требуют решения оператора ПДн.
3. Отложенная доставка теперь повторно проверяет привязку, активность и версию
   аккаунта до отправки. Отключение/перепривязка/отзыв блокируют старый ответ.
4. `FLOWOPS_AI_ALLOW_SENSITIVE=false` применено в рабочем .env; запуск подтверждён
   журналом. Маскирование не гарантирует обнаружение всех ПДн и не заменяет
   правовое основание обработки внешним сервисом.
5. Эксплуатационные требования вне кода: фактическая локализация БД/резервных
   копий, правовые основания и цели обработки, сроки хранения/удаления,
   договоры с обработчиками, матрица доступов, порядок реагирования на утечки,
   аудит и ответственность оператора должны быть подтверждены отдельно.
