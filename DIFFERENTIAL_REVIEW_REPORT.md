## Блокеры промышленного запуска, существовавшие до патча

### DR-P01 — High: просмотр всех заявок не требует идентификации

**Доказательства:** `cmd/server/main.go:82`, `:83`, `internal/security/operator.go:17`, `internal/handlers/tickets.go:434`, `:472`.

**Атакующий:** любой клиент, имеющий сетевой доступ к API, без операторского токена. В корпоративной сети это может быть обычный сотрудник или скомпрометированный компьютер.

**Сценарий:** `GET /api/tickets` возвращает общую выборку с адресами, исходным текстом, callback URL и ответами; `GET /api/tickets/1` раскрывает конкретную заявку. SQL не содержит фильтра владельца/подразделения. Новое middleware пропускает эти GET-запросы.

**История:** маршруты и отсутствие проверки владельца есть в `d6e643b`; коммит их не вводит. Фильтрация истории в браузере не является контролем доступа.

**Исправление:** идентифицировать сотрудников на сервере; проверять право чтения каждого объекта; выдавать отдельные ограниченные представления сотруднику и оператору. Один сетевой SSO перед приложением подтверждает личность, но сам по себе не проверяет права на конкретную заявку. Снизить возвращаемый набор полей и ввести пагинацию.

### DR-P02 — High: подтверждение решения можно подделать без токена

**Доказательства:** `cmd/server/main.go:86`, `internal/security/operator.go:17`, `internal/handlers/tickets.go:133`, `:147`, `:151`.

**Сценарий:** клиент без токена отправляет `POST /api/tickets/1/feedback` с `{"resolved":true}`. Handler обновляет статус по ID без проверки личности, владельца и предыдущего состояния. Можно также отправить `false`, изменив чужой статус на `assigned_to_operator`.

**История:** это существовало до патча; оно не является вновь внесённой регрессией. Патч улучшает начальный статус, но не обеспечивает достоверность последующего подтверждения.

**Исправление:** связь заявки с автором, проверка прав и допустимых переходов состояния; для каналов — привязанное к конкретному пользователю/заявке подписанное подтверждение с ограниченным сроком и защитой от повторов.

### DR-P03 — High: сохранённый callback URL используется как адрес серверного запроса

**Доказательства:** `internal/handlers/tickets.go:91` сохраняет `request.CallbackURL`; `:204`, `:221`, `:268`, `:272` используют его при операторском ответе. В `internal/security/operator.go:17` публичный ingest не защищён.

**Сценарий:** доступный клиент создаёт заявку через `/api/v1/ingest` с адресом своего приёмника или внутреннего HTTP-сервиса. Когда оператор отвечает, сервер выполняет POST по сохранённому адресу. Это отложенный путь SSRF и отправки операторского ответа по адресу, выбранному отправителем. Автоматического запроса сразу при ingest здесь нет; требуется действие оператора.

**История:** сохранение callback и `sendWebhook` существовали до коммита. Запрет редиректов в AI-клиентах не распространяется на отдельный HTTP-клиент webhook. Свежая локальная proof-проверка основного аудита подтвердила: после HTTP 307 второй loopback-сервер получает POST с текстом операторского ответа. Реальные внутренние сервисы компании не опрашивались.

**Исправление:** интеграции и их адреса регистрирует доверенный администратор; клиент передаёт ID интеграции. Ограничить схемы/хосты/порты, сетевую доступность и редиректы, проверять фактическое подключение, подписывать webhook; не считать строковую проверку hostname достаточной защитой от DNS rebinding.

## Новое ограничение доступности, требующее продуктового решения

### DR-O01 — Общий бюджет анализа позволяет одному источнику вытеснить остальных

`internal/analyzer/analyzer.go:78` вызывает `acquireModelSlot` до проверки наличия любого провайдера. `internal/analyzer/guard.go:154` ограничивает весь экземпляр 60 анализами в минуту и четырьмя параллельными обработками. После исчерпания бюджета возвращается General/manual review, даже если можно было бы выполнить локальную эвристику. Бюджет общий для web, почты и ботов; идентификация источника отсутствует.

Последовательность подтверждена свежей локальной proof-проверкой: без AI-ключей после 60 обычных анализов 61-й переводится в ручную проверку, хотя локальная классификация не требует внешнего ресурса. `TestCapacityLimitFailsToHumanReview` также подтверждает предусмотренную реакцию на заполнение слотов/бюджета, но не проверяет справедливость между пользователями.

Это явно выбранный защитный fallback, а не доказанная новая High/Critical уязвимость: до патча анонимный источник мог без лимита вызывать платные провайдеры. Для компании следует разделить квоты внешнего AI и доступность локального разбора, добавить лимиты по подтверждённому пользователю/интеграции, очередь, квоты каналов и метрики отказов. Данный пункт не следует выдавать за установленную регрессию безопасности.

## Рекомендации и границы уверенности

Сначала закрыть чтение/изменение чужих заявок и доверие к ingest/callback, затем внедрить персональные роли, проверяемые переходы статусов, журналирование действий конкретных субъектов и изоляцию каналов. Не ослаблять внесённый fail-closed режим ради удобства запуска.

Сохранить положительные изменения этого коммита; дополнить реальные интеграционные и браузерные тесты. Проверка production требует отдельно изучить корпоративный SSO/proxy, egress, DNS, секреты, права PostgreSQL, резервное копирование/восстановление и разрешения на передачу данных провайдерам. Такие настройки этим diff не доказываются. Уровень уверенности высокий в перечисленных потоках кода и разграничении old/new; средний в полноте статического анализа; реальная эксплуатационная устойчивость здесь не установлена.

Отчёт создан без изменений runtime-кода и без отправки реальных заявок внешним провайдерам.
