## High — блокеры запуска

### SEC-001. Все заявки доступны без входа и проверки владельца

- **Правила:** GO-AUTH-001 / GO-AUTHZ; конфиденциальность объектов.
- **Доказательства:** `cmd/server/main.go:82–91` регистрирует GET tickets/detail/audit/stats; `internal/security/operator.go:17–21` пропускает их без токена. `internal/handlers/tickets.go:434–469` выбирает все строки и исходные тексты, email, callback и ответы оператора; `:472–490` получает любой объект по ID. `web/app.js:61–65` загружает всю базу заявок и лишь затем фильтрует её в браузере по введённому email.
- **Сценарий:** любой посетитель с доступом к API выполняет `GET /api/tickets`; фильтр интерфейса и знание токена оператора не нужны. Получает обращения других сотрудников, включая финансовые сведения.
- **Проверка:** overlay-тест подтвердил проход анонимного запроса через фактическое middleware. Полный ответ из PostgreSQL не воспроизводился; отсутствие WHERE по пользователю установлено по SQL и маршрутам.
- **Исправление:** обязательная идентификация для всего бизнес-API; проверка владельца/роли/отдела на сервере в List и Detail; постраничная выдача и минимальный состав полей. UUID не заменяет авторизацию.
- **Условия:** отдельный шлюз мог бы запретить анонимный доступ, но общий вход всех сотрудников не заменяет объектные права. Конфигурация такого шлюза не предоставлена.

### SEC-002. Любой посетитель может закрыть или переоткрыть чужую заявку через feedback

- **Доказательства:** `internal/handlers/tickets.go:133–158`: POST с `resolved=true` устанавливает `auto_resolved`, иначе `assigned_to_operator`; WHERE содержит только ID. Нет владельца и допустимого предыдущего состояния. Middleware в `internal/security/operator.go:18` этот POST не защищает.
- **Сценарий:** POST `/api/tickets/1/feedback` с `{"resolved":true}` подделывает успешное решение; `false` возвращает в очередь даже закрытый тикет. ID можно получить через SEC-001.
- **Влияние:** нарушение целостности очереди, отчётности и подтверждения решения. Это не выполнение финансовой операции, но блокер рабочего процесса компании.
- **Проверка:** анонимный проход middleware воспроизведён; SQL-переход проверен статически, без изменения реальных данных.
- **Исправление:** только подтверждённый владелец либо разрешённый сотрудник; проверяемая машина состояний; защита от повторов и конкурентного изменения; транзакция с предикатом текущего статуса и аудитом.

### SEC-003. Сохранённый callback позволяет серверный запрос к произвольному адресу

- **Правило:** GO-SSRF-001.
- **Доказательства:** публичный Ingest принимает и сохраняет `callback_url` (`internal/handlers/tickets.go:74–108`). Update/Reply запускают `sendWebhook` (`:204–222`, `:262–278`). Отдельный HTTP-клиент не проверяет адрес, сеть и redirects.
- **Сценарий:** атакующий создаёт правдоподобную заявку с callback на внутренний HTTP-сервис или на свой адрес с HTTP 307. Когда оператор отвечает, приложение отправляет JSON с ответом от своего сетевого положения. Разрешены loopback и внутренние сети, перенаправления следуют автоматически.
- **Проверка:** действительный `sendWebhook` в изолированном тесте прошёл 307 и отправил POST с синтетическим ответом на второй loopback-сервер. Цепочка требует ответа оператора; не утверждается, что один анонимный запрос немедленно вызывает callback. Нет доказательства чтения cloud metadata или произвольного RCE.
- **Исправление:** callback-регистрации только доверенным интеграциям, фиксированный allowlist HTTPS endpoint; запрет redirects; проверка разрешённых адресов при подключении, включая IPv6/DNS rebinding; egress firewall. Для легитимных внутренних интеграций — узкий согласованный allowlist, а не разрешение всех private IP. Подписывать исходящие события и ограничить очередь.

### SEC-004. MAX по умолчанию не проверяет сертификат сервера

- **Правило:** GO-TLS-001; небезопасное значение по умолчанию.
- **Доказательства:** `cmd/server/main.go:72`, `.env.example:23`, `docker-compose.yml:48` задают `MAX_INSECURE_TLS=true`; `internal/channels/channels.go:58–62` включает `InsecureSkipVerify`; `internal/channels/max.go:57–61` передаёт Authorization.
- **Сценарий:** атакующий на сетевом пути/с контролем DNS предъявляет поддельный сертификат и получает токен бота и содержимое сообщений, может подменять обновления. Это требует сетевой позиции, а не знания публичного URL.
- **Проверка:** локальный HTTPS-сервер с недоверенным сертификатом получил синтетический токен при текущем insecure-режиме. Default=true подтверждён тремя точками настройки.
- **Исправление:** проверка TLS обязательна в рабочем режиме; ошибочные boolean-конфигурации должны останавливать запуск. Нужный корпоративный CA устанавливается отдельно. Не заменять проблему сертификата отключением проверки.

### SEC-005. Маскирование не обеспечивает границу передачи чувствительных данных в LLM и KB

- **Доказательства:** `internal/security/pii.go:22–34` использует конечный набор regex; email-шаблон в `:23` регистрозависим. В `internal/analyzer/analyzer.go:85–125` результат маскирования уходит провайдеру, а отказ GigaChat допускает Gemini без отдельной политики для класса данных. `internal/analyzer/guard.go:121–129` разрешает KB-ответ, если тот же MaskPII не нашёл ПДн; `internal/knowledge/knowledge.go:248–293` выбирает регламент по тексту/предсказанному отделу, а не правам сотрудника.
- **Воспроизведение:** `Contact IVANOV@EXAMPLE.COM about VPN` и синтетическая строка `Сотрудник Иван Петров, зарплата 250000 рублей, счёт 40702810900000000001` остаются неизменными после MaskPII и проходят CheckPromptInput. Поэтому regex-фильтр не доказывает обезличивание ни запросов, ни регламентов.
- **Влияние:** чувствительные сведения могут уходить внешней модели/резервному провайдеру и попадать в автоматический ответ из регламента. Разрешение использовать модель не означает автоматического разрешения на любые категории данных и любой fallback.
- **Исправление:** явная политика разрешённых провайдеров и категорий данных; fail-closed при неизвестной категории/провайдере; возможность локальной обработки; запрет несогласованного fallback. Исправить конкретные пропуски regex, но не объявлять это универсальной анонимизацией. Отделить опубликованные для пользователей регламенты от внутренних/ограниченных; права доступа проверять до retrieval.
- **Граница вывода:** фактическая отправка реальных ПДн не выполнялась и не утверждается; юридическое соответствие и договоры провайдеров данным аудитом не подтверждаются.

### SEC-006. Используемая локальная Go-сборка и зависимости имеют известные advisories

- **Доказательства:** локально `go1.25.1`; `go.mod` фиксирует pgx/v5 `v5.7.1`, x/text `v0.18.0`. govulncheck v1.10.0 проверил именно Go 1.25.1: 48 результатов достижимости символов, ещё 5 результатов уровня импортированных пакетов и 34 уровня модулей. Полный вывод и сводка сохранены в `reports/security-audit-2026-11-23/`.
- **Точность интерпретации:** это не 48 подтверждённых эксплуатаций. Например, [GO-2026-5004](https://pkg.go.dev/vuln/GO-2026-5004) в pgx требует simple protocol и dollar-quoted SQL с placeholder-путаницей; таких запросов/настройки в проекте не найдено. [GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970) требует некорректного UTF-8; CheckPromptInput отклоняет его до нормализации, что снижает прямую доступность. [GO-2026-6629](https://pkg.go.dev/vuln/GO-2026-6629) отмечен через pgx/precis, и применимость конкретного Nickname-профиля требует отдельной проверки. HTTP/2 advisories нельзя автоматически приписывать HTTP/1 listener.
- **Исправление:** выбрать поддерживаемый Go и актуальный security patch; как нижние границы конкретных advisories сканер указал Go 1.26.11, pgx/v5 5.9.2 и x/text 0.41.0. Это не рекомендация заморозить версии навсегда: проверить совместимость и актуальные исправления при обновлении. Проверять финальный Linux binary/container, добавить CI govulncheck и политику обработки findings.
- **Условия:** `Dockerfile:1` использует плавающий `golang:alpine`; фактический Go production-образа неизвестен. Windows-результат не выдаётся за скан готового Linux-образа. Первоначальный запуск сканера автоматически выбрал более новый Go; итоговый отчёт специально получен отдельным scanner binary с `GOTOOLCHAIN=local`.

### SEC-007. Ingest доверяет подставленным отправителю, каналу и адресу назначения

- **Доказательства:** `internal/handlers/tickets.go:74–108` принимает `sender/channel/callback_url` от любого сетевого клиента. `internal/channels/dispatcher.go:18–40` использует сохранённого отправителя для адресации ответа. `internal/channels/email.go:146–166` извлекает идентичность из From; приложение не связывает её с корпоративным сотрудником. Telegram/MAX workers также не имеют списка разрешённых сотрудников/чатов (`telegram.go:100–124`, `max.go:129–159`).
- **Сценарий:** злоумышленник представляет заявку как email/bot от другого человека, либо указывает свой адрес и создаёт правдоподобный контекст. Оператор, доверившись отображаемой личности, отправляет ответ через корпоративные каналы не тому адресату. Возможны обращения посторонних к внутренним регламентам. Для HTTP ingest подделка маршрута полностью определяется входным JSON.
- **Исправление:** отдельные ключи/подписи интеграций с replay-защитой; канал и связанный сотрудник определяются сервером; адреса доставки из проверенного справочника. Для почты — проверенная граница корпоративного MTA и политика доверия к результатам проверки, а не свободному From. Для ботов — подтверждённая привязка chat/user к сотруднику и ограничения групп.
- **Условия:** DMARC/антиспам могут работать на почтовом сервере, но их политика неизвестна. Маскирование Sender не аутентифицирует его. Внешние сообщения в проверках не отправлялись.

### SEC-008. Демонстрационная конфигурация PostgreSQL предоставляет приложению административный доступ

- **Доказательства:** `docker-compose.yml:6–7,33` использует стандартную административную роль и фиксированный демонстрационный пароль (значение здесь не повторяется); тот же DSN получает приложение. `internal/database/db.go:35–100` выполняет DDL при каждом запуске; `internal/handlers/tickets.go:292–300` содержит TRUNCATE и удаление пользовательских регламентов. В runtime нет отдельной роли миграций.
- **Влияние:** компрометация процесса приложения затрагивает всю БД; общий операторский токен даёт также массовое удаление. Это усилитель последствий, а не доказанный удалённый обход пароля. Порт БД в Compose ограничен loopback, поэтому удалённый доступ к PostgreSQL из интернета не заявляется.
- **Исправление:** отдельный миграционный job/роль; runtime-role только с нужными операциями; уникальные секреты через secret manager; отдельное административное право на reset, отключение demo reset в production. Подтверждённые backups и восстановление. Проверка прав реальной БД обязательна до допуска.

## Medium — существенные эксплуатационные риски

### SEC-009. Лимит ИИ не ограничивает создание/хранение заявок и глобально вытесняет пользователей

- **Доказательства:** Create/Ingest ограничивают HTTP body до 1/2 MiB (`tickets.go:39,76`), но после отказа анализа заявки всё равно сохраняются (`:50–58,96–108`). Лимит текста 16 KiB в анализаторе направляет на ручную обработку, а не отвергает запись. List без LIMIT (`:434–469`); `web/app.js:63` повторно загружает весь массив. `analyzer.go:78` / `guard.go:154–170` применяют 60/min и 4 slots на весь процесс, включая локальный режим без AI.
- **Проверка:** 61-й последовательный синтетический запрос без ключей попадает в General/manual review. БД не заполнялась нагрузкой. Публичный flood может вытеснять другие каналы и наращивать хранилище; масштабный DoS не измерялся.
- **Исправление:** лимиты на идентичность/интеграцию и общий ingress; reject oversized до хранения; квоты/очереди и backpressure; пагинация; retention. Отдельно лимитировать внешнюю модель, сохраняя безопасную локальную классификацию. Общие лимиты при нескольких репликах.

### SEC-010. Общий токен не даёт персональных ролей и надёжного аудита

- **Доказательства:** `internal/security/operator.go:13–38` сравнивает один общий токен; проверяет длину, но не энтропию и не срок действия. В audit (`tickets.go:220,252`, `knowledge.go:112,172–174`) actor — константа `operator`, ошибки записи игнорируются. Изменения статуса/отдела, удаление KB и reset не имеют полноценного события с before/after и субъектом.
- **Влияние:** нельзя установить конкретного сотрудника, ограничить его отделом/действием или индивидуально отозвать доступ. Потерянный токен разрешает все защищённые операции, включая reset.
- **Исправление:** SSO/OIDC либо другой согласованный механизм идентификации; индивидуальные роли/группы и серверная авторизация; ротация/отзыв сессий, отдельные credentials интеграций. Аудит изменения и события в одной транзакции или надёжном outbox, запись actor/object/result/request ID и политика хранения.
- **Не ложная находка:** сравнение SHA-256 constant-time реализовано корректно; длинный криптографически случайный токен не считается реально подбираемым. Риск — объём полномочий, утечка и отсутствие индивидуальной ответственности.

### SEC-011. Заявка закрывается до гарантированной доставки ответа

- **Доказательства:** `internal/handlers/tickets.go:241–260` сохраняет статус closed до фоновой отправки; ошибка только журналируется. PATCH-ветка `:200–223` сохраняет operator_reply, но вызывает только webhook, а не channel dispatcher. Нет persistent outbox, idempotency или статуса доставки. Email/боты полагаются на внешнюю отправку без устойчивого восстановления состояния.
- **Влияние:** сотрудник может не получить решение, а заявка и метрики уже показывают закрытие. Повтор может дать дубли. Для финансового/корпоративного процесса это риск целостности и доступности, а не доказанная кража денег.
- **Исправление:** транзакционный outbox и job с контролируемыми повторами, idempotency key, отдельные состояния resolution/delivery; единая семантика PATCH/Reply; подтверждение/видимая оператору ошибка и мониторинг недоставленных ответов. Integration-тест с отказом SMTP/бота и перезапуском worker.

### SEC-012. После SMTP-подключения нет дедлайна сетевых операций

- **Доказательства:** `internal/channels/email.go:273–324`: TLS Dialer имеет timeout только на соединение; smtp.NewClient/Auth/Mail/Rcpt/Data/Quit не получают context/deadline. ctx проверяется лишь после записи. В connectIMAP `:49–59` greeting также читается до установки deadline в command `:72`.
- **Влияние:** зависший/скомпрометированный сервер после соединения может остановить почтовый worker или удерживать goroutine ответа значительно дольше 15 секунд. Без верхнего лимита задач накопление повышает риск исчерпания ресурсов.
- **Исправление:** deadline на весь сетевой сеанс и закрытие conn по ctx.Done; ограничения параллелизма; отдельный worker с retry/backoff и метрикой задержки. Для IMAP — deadline ещё до greeting. Реальные почтовые серверы не тестировались; вывод основан на явном отсутствии deadlines.

## Дополнительные условия допуска

- **Размещение:** прямой запуск слушает `:8080` на всех интерфейсах (`cmd/server/main.go:99`), хотя Compose публикует loopback. README с localhost не является ограничением listener. Настроить явный bind и закрыть обход шлюза. TLS/SSO на edge неизвестны, поэтому их наличие/отсутствие не выдано за подтверждённую уязвимость конкретной production-среды.
- **Браузер:** основные текстовые поля экранируются, подтверждённого stored XSS не найдено. escapeHTML не является универсальным encoder для HTML-атрибутов; текущие динамические priority/ID ограничены сервером, filename требует внимания при внешнем изменении файлов. CSP/frame protection/nosniff не видны в приложении; проверить edge. Только static и защищённые маршруты явно ставят no-store; чувствительные JSON-ответы тоже должны иметь политику cache.
- **Файлы/контейнер:** runtime Dockerfile не задаёт USER; образ собирается из плавающего Go tag, внешние CA скачиваются без закреплённого digest. Зафиксировать и регулярно обновлять образы, запускать непривилегированно с минимальными mount/сетевыми правами. CA-политика должна быть согласована компанией, а не изменяться незаметно при каждой сборке.
- **KB:** validation фраз не подтверждает правильность регламента. Нужны утверждение, версии, публикация по аудитории и откат. Успешная ветка ReplaceWithOptions в обычных тестах имеет 0% покрытия; проверена только сохранность при отклонении. Конкурентное добавление файлов/много процессов и согласованность файлов с индексом требуют отдельных тестов.
- **Данные:** сырые заявки хранятся без маскирования, что может быть необходимо для работы, но требует ACL, согласованного retention, защиты резервных копий и ограничений доступа к дискам/БД. Шифрование хранилища и восстановление backup не проверены.
- **Заявления интерфейса:** `tickets.go:322` возвращает фиксированное утверждение о «152-ФЗ / РФ Контур + PII Guard», несмотря на возможность Gemini. Это нельзя использовать как свидетельство соответствия; отображать фактический режим и согласованную политику. Юридическая оценка в этот аудит не входит.

## Что уже работает

Модель не получает KB и не имеет инструментов исполнения. Классификационный JSON ограничен и проверяется. AI redirects запрещены, размеры ответов/время ограничены. Привилегированные маршруты при отсутствующем/коротком токене закрыты. Небезопасное обновление KB не удаляет прежний файл. При создании автоответ требует подтверждения. Эти свойства стоит сохранить, но SEC-002 обходится отдельным endpoint и не делает подтверждение доверенным.

## Порядок исправлений и критерии повторного допуска

1. Сначала SEC-001/002/007: единая идентификация и серверные права. Тестовая матрица anonymous / сотрудник A / сотрудник B / оператор отдела / администратор / интеграция, включая прямые HTTP-запросы в обход UI. Чужие данные и переходы должны отвергаться.
2. SEC-003/004/005: закрыть произвольный egress, обязательный TLS MAX, политика чувствительных данных и allowlist провайдеров. Тесты loopback/private/IPv6/redirect/rebinding, неверных сертификатов, отсутствия разрешения на fallback и утечек маскирования.
3. SEC-006/008: обновить и закрепить security baseline/toolchain, проверить финальный образ; минимальные DB права и отдельные миграции. Разобрать каждый scanner finding: fix либо доказанная неприменимость с владельцем и сроком пересмотра.
4. SEC-009–012: квоты/пагинация, надёжный аудит и outbox, deadlines. Проверки отказов доставки/БД, конкурентных переходов, восстановления процесса и нагрузочного бюджета.
5. Перед запуском согласовать deployment, SSO, категории данных, провайдеров, доступы отделов, retention, RPO/RTO и процедуру инцидентов. Повторный независимый аудит и пентест на изолированном staging с близкой к production конфигурацией.

Критерий допуска — закрытые High-находки и проверенная конфигурация с воспроизводимыми отрицательными тестами, а не только зелёный go test. Изменение пользовательских сценариев и механизма входа требует отдельной задачи реализации; текущий запрос был на аудит.
