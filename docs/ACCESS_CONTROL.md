# Роли и рабочие пространства

Каждая компания получает изолированное рабочее пространство. Персональный доступ состоит из имени, email, роли и пароля. Случайный код используется для первичной активации и восстановления. В PostgreSQL хранится SHA-256 хеш кода, а полный код показывается только при создании или перевыпуске. Это высокоэнтропийный код, не пароль пользователя.

| Возможность | Сотрудник | Оператор | Аналитик | Администратор |
|---|---|---|---|---|
| Создать обращение | Да, от своего имени | Да | Нет | Да |
| Читать обращения | Только созданные своим профилем | Очередь компании | Нет | Очередь компании |
| Подтвердить автоответ | Только своё обращение | Да | Нет | Да |
| Ответить, назначить отдел и приоритет | Нет | Да | Нет | Да |
| Читать и добавлять регламенты | Нет | Да | Нет | Да |
| Удалять регламенты и очищать данные | Нет | Нет | Нет | Да |
| Агрегированная аналитика | Нет | Нет | Да | Да |
| Каналы, ключи, импорт, настройки | Нет | Нет | Нет | Да |
| Команда, роли, отзыв и перевыпуск кодов | Нет | Нет | Нет | Да |
| Журнал действий | Нет | Нет | Нет | Да |

## Первый запуск и демонстрация

1. Активируйте вход по почте и паролю с существующим кодом компании (`FLOWOPS_OPERATOR_TOKEN` для default) либо создайте новую компанию на экране входа. Создание новой компании не позволяет присоединиться к чужой компании.
2. Существующий код компании — доступ владельца с ролью администратора. Он сохраняется для совместимости и начальной настройки. Не выдавайте его всем участникам.
3. В разделе «Администрирование» добавьте участников с рабочим email и нужной ролью. Создание участника не отправляет письмо: передайте одноразово показанный персональный код вручную.
4. Активируйте профиль кодом участника, затем входите по почте и паролю. Навигация и начальный раздел зависят от роли. Аналитика отделена от операторской очереди.
5. Для отзыва нажмите «Отключить»; для утраченного кода — «Новый код». Перевыпуск аннулирует предыдущий код. Список команды никогда не возвращает полные коды или хеши.

Роль и активность читаются из базы на каждом запросе. Изменения не зависят от состояния интерфейса. Запрет API возвращает 403, отсутствие входа — 401, чужое обращение или пользователь другой компании — 404. Неизвестные маршруты по умолчанию запрещены для ограниченных ролей.

Email в форме сотрудника не является доказательством личности: сервер сам берёт email профиля и записывает `requester_id`. Список и отдельная заявка фильтруются по идентификатору профиля и компании. Исторические обращения и обращения внешних каналов не привязываются к профилю только по совпадению email.

## Ограничения текущего этапа

Реализован контур ролей для хакатонного продукта с несколькими компаниями, а не готовая корпоративная IAM-платформа. Вход выполняется по почте и паролю с восьмичасовыми cookie-сеансами; SSO, MFA, проверка почтового ящика и доставка приглашений не реализованы. Подробности: [аутентификация](AUTHENTICATION.md). Владелец остаётся отдельным bootstrap-доступом. Подтверждённая привязка Telegram/MAX/почты к профилям сотрудников требует отдельного процесса проверки личности.

## Проверки

`FLOWOPS_TEST_DATABASE_URL` должен указывать на отдельную базу `flowops_security_test`. Тесты создают временные схемы и удаляют их после завершения.

`go test ./...` покрывает матрицу ролей, серверный запрет обхода, изоляцию компаний и заявок, подмену email, запрет самоповышения, отзыв, смену роли и перевыпуск кода, отсутствие секретов в списке команды, сохранение scoped ingest и CORS preflight виджета. В браузере проверены четыре кабинета в отдельном тестовом пространстве «FlowOps — проверка ролей».

Дополнительные исправления: импорт больше не падает при длинном Unicode-заголовке и не отправляет чувствительный исходный текст модели при запрещённой обработке; email канала нормализуется перед проверкой уникальности; создание компании и её настроек выполняется одной транзакцией; данные и показанные коды очищаются при смене сеанса.
