# Вход по рабочей почте и паролю

## Первый вход

1. Администратор создаёт участника с именем, рабочей почтой и ролью в разделе «Администрирование» и передаёт ему код активации.
2. Участник вводит рабочую почту и выданный код в обычную форму входа, в поле «Пароль или код приглашения». После проверки сайт сам раскрывает установку пароля, переносит код и почту; остаётся дважды задать новый пароль. Для ручного восстановления доступна ссылка «Восстановить пароль». Код привязан к профилю и компании, роль не выбирается пользователем.
3. После активации вход выполняется по почте и паролю. Персональный код становится недействительным.

Владелец новой компании задаёт почту и пароль после её создания, используя выданный резервный код владельца. Существующий `FLOWOPS_OPERATOR_TOKEN` активирует администратора default-компании. Сохранённые старой версией браузерные коды автоматически переносятся в форму активации и удаляются из localStorage/sessionStorage.

Один email может иметь независимые профили в разных компаниях. При совпадающем пароле сайт предложит выбрать компанию после проверки пароля. Если профилей больше восьми, укажите идентификатор компании: администратор видит его в своём разделе. Список компаний не возвращается по одному лишь email без правильного пароля.

## Восстановление

Администратор нажимает «Сбросить пароль» у участника и передаёт ему новый код. Прежний пароль и открытые сеансы отзываются; пользователь снова задаёт пароль через форму активации. Отключение и последующее включение участника не восстанавливает старые сеансы.

Для единственного администратора предусмотрен резервный код владельца: в форме активации он позволяет восстановить существующий административный профиль той же компании. Код владельца остаётся привилегированным bootstrap-доступом, его нельзя выдавать сотрудникам. Восстановление через письмо и проверка владения почтовым ящиком пока не реализованы.

## Реализация

- Пароль: минимум 12 символов, максимум 72 байта, без обрезания; bcrypt cost 12 и индивидуальная соль. Используется официальный [пакет golang.org/x/crypto/bcrypt](https://pkg.go.dev/golang.org/x/crypto/bcrypt).
- Сеанс: случайный 256-битный идентификатор; в PostgreSQL хранится только SHA-256 хеш. Срок — восемь часов, проверяется сервером.
- Cookie `flowops_session`: HttpOnly, SameSite=Strict, Path=/. Браузерный код не получает идентификатор сеанса. JavaScript-хранилища не используются для пароля или сеанса.
- Состояние изменяется с отдельным CSRF-токеном, привязанным к конкретному сеансу; сервер проверяет Origin. Вход и активация принимают только ограниченный JSON с того же origin.
- Роль и активность читаются на каждом запросе. Версия учётных данных делает старые сеансы недействительными даже при гонке входа со сбросом пароля.
- Ограничение попыток: 15 в минуту на email, 60 на IP; не более четырёх одновременных операций bcrypt на процесс. Ограничитель локальный, для нескольких реплик потребуется общий лимитер.
- API-ключи интеграций остаются отдельным механизмом. Bootstrap bearer-коды сохраняются для совместимости API, а интерфейс использует cookie-сеансы.

При доступе по HTTPS, в том числе через TLS-прокси, задайте `FLOWOPS_COOKIE_SECURE=true`. Для локального `http://localhost:8080` используется false. Приложение не доверяет произвольному X-Forwarded-Proto.

## Проверки

Тесты с отдельной PostgreSQL-базой покрывают активацию, привязку почты, одноразовость кода, bcrypt, cookie-флаги, CSRF и Origin, неверные пароли, одинаковые ответы для неизвестной почты, выбор компании, истечение и отзыв сеанса, смену роли, сброс и восстановление владельца. Браузерная проверка: вход, обновление страницы, запись обращения с CSRF, выход, форма активации и мобильная ширина 390px.

Регистрация новой компании по умолчанию свёрнута в компактную плашку под кнопкой входа; восстановление пароля находится ниже. Регрессионный тест `TestInvitationCodeInLoginOffersActivation` воспроизводит ввод приглашения вместо пароля, проверяет переход к активации без открытия сеанса, последующий вход по паролю и отказ повторно использованному коду.

## Разные аккаунты в соседних вкладках

Cookie входа общая для вкладок одного профиля браузера. Для одновременной работы администратора и сотрудника нужны разные профили браузера либо отдельное приватное окно. Роль участника не меняется при активации его персонального приглашения.

Вкладка сохраняет только публичный ID своего участника в `sessionStorage` и передаёт его как `X-FlowOps-Member`. Сервер продолжает определять права по HttpOnly cookie и базе; ID не является credential и не выдаёт доступ. Если cookie уже принадлежит другому участнику, запрос отклоняется с HTTP 409 и кодом `session_changed`. Вкладка очищает отображаемые данные и просит повторный вход, сохраняя привязку при перезагрузке. Активация и явный вход сверяют полученную cookie с пользователем из ответа сервера. Устаревшая вкладка также не может завершить сеанс другого аккаунта.

Регрессия покрыта `TestEmailPasswordsSessionsAndRevocation` и `node --test tests/ui-session.test.cjs`: роль после активации, конфликт идентичностей при запросе профиля, аналитики и выходе, защита от незаметной смены пользователя при опросе, активации и перезагрузке.
