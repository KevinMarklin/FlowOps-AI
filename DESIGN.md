# FlowOps workspace

Mode: Operate. An employee or support operator uses the application at a desk; light working surfaces keep long forms and queues readable, with a navy brand header.

Palette retained: ink #102a43, action #0b5367, blue #147d92, teal #32a7a0, background #f4f7fa, white #ffffff. Secondary text #526d82.

Typography: locally served Golos Text, regular through bold, with Cyrillic coverage. Headings use medium weight and restrained negative tracking. Numbers use tabular figures.

Desktop navigation is a persistent left rail; below 850px it becomes horizontal scrolling navigation. Content leads with a compact heading, followed directly by the task. Employee request form is primary; the result and history form a secondary column. Mobile collapses these into one column. Metrics share a single summary surface.

No decorative eyebrows, section numbering, sparkle symbols, gradient backgrounds or display-serif headings. Teal identifies actions and selection. Forms and meaningful groups use borders; typography and spacing carry the rest.

Logo provenance: generated in the dedicated FlowOps AI logo chat, 01a2189e-abcd-7eb3-8c7b-beeb14d9857f, standalone nested-F variant. Original PNG is shipped unchanged as web/assets/flowops-mark.png. Font source: Google Fonts Golos Text, OFL license included alongside font files.

Role-aware surfaces: employee requests, operator queue and regulations, analyst aggregates, administrator membership and settings. Analytics is a separate section. Navigation includes only granted surfaces, matching server permissions. The administrator landing surface prioritizes inviting the team and managing access. Personal codes appear once and are removed from DOM on session changes.

Authentication: email/password is primary. First-time activation and password recovery expand inside a native details section; new-company creation remains below. Keep password-manager autocomplete and visible labels. Never store session secrets in JS storage.

Workflow refinement: employees have a full-width workspace without a redundant single-item rail. The request form explains useful input; the result leads with its actual outcome (regulation, specialist handoff, or completed response), followed by the summary, responsible department and priority. Source instructions stay readable after confirmation or escalation. History has text/ID search; the operator queue combines search, priority, department and status. Source text and reply composition use native disclosure controls; drafts survive polling. Navy, teal and Golos Text remain the visual identity. The implementation lives in workflow.css and the existing app.js; mobile stacks the employee flow and queue filters.

Personal settings open from an accessible three-line icon in the top-right header. A native dialog contains theme selection and employee Telegram/MAX connections. Light and dark themes use the same navy/teal identity; dark surfaces use #101e2a and #1a2c3b with #e0edf7 text. Theme preference is local to the browser. Connection codes are displayed temporarily, never persisted in browser storage, and cleared on close or account change. Mobile preserves the header name and keeps the dialog within the viewport.

Connection refinement: Telegram offers a direct, short-lived bot link after code issuance, with manual copying as fallback. Pending actions cannot be submitted twice; stale responses cannot restore cleared codes. History and queue use bounded pages with explicit older/latest navigation. Search runs on the server across accessible history by exact ID, word or phrase, including transcript messages.

Pilot evidence: the operator action opens the reply editor and begins visible work measurement, with an explicit pause. Analytics separates observed operator minutes, routing changes and hypothetical savings. Six metrics form a three-column desktop layout, two columns on medium widths and one on mobile.

University intake refinement: preserve the established Golos Text, navy #102a43, action #0b5367, blue #147d92, muted #526d82, white #ffffff and background #f4f7fa. A blue left rule marks the optional clarification stage inside the existing request form; it is a continuation of the request, rather than a modal or a second ticket. The employee gives a location, symptom, work impact and checks only when explicit facts are missing. Three task examples lead with classroom equipment, service access and a study certificate. Labels remain left aligned, keyboard focus moves to the first unanswered field, mobile stacks naturally, and dark mode keeps the same hierarchy. The operator sees requester context immediately above routing controls. No university crest or claim of an official deployment is added.

Organization-aware intake: a three-step horizontal guide and domain-specific examples precede the primary form. Steps and examples stack on narrow screens; the form leads, then the result and personal history. Domain titles and examples come from the workspace profile. Registration offers education, bakery, bank and other; starter instructions explicitly require adaptation. Current departments populate assignment and knowledge controls. Clarifications can be cancelled without losing the original message. The result uses a tinted working surface, readable routing details and direct confirmation actions. History uses disclosure rows; queue filters share one surface. Light/dark and desktop/mobile retain the same content hierarchy. Implementation: service-flow.css and docs/service-flow.md.

Support conversations: dialogue.js and dialogue.css provide a persistent, bounded transcript after the routing summary, with employee, assistant, specialist and status labels. New messages follow the latest content while readers can scroll older messages. The composer remains available until closure. Two requester actions, “Вопрос решён” and “Не помогло”, are separate from answer-specific 1–5 ratings and optional comments. The operator sees feedback and opens a persistent composer above the queue. Preserve drafts on polling, ticket switches and failed sends; clear them on session changes. The established theme, responsive stacking and visible focus treatment apply throughout. Details and verification: docs/support-dialogue.md.

Ticket register: follow the supplied reference's structure within the existing palette. Collapsed tickets are 72px horizontal rows: compact status at left, ID and single-line subject in the center, date at right and a reserved final position for a static yellow unread dot. Detailed routing, replies and closing controls remain inside native disclosure rows. Keep expanded rows stable through polling. Mobile places the date below the subject. Personal history uses the same row structure. The dot means a new open ticket or an employee message not yet read by this operator; opening the transcript acknowledges only the message IDs actually received. Read state persists on the server and remains separate for each operator. Implementation: ticket-rows.css.

Personal queue: “Очистить мой список” hides existing tickets only for the signed-in operator or administrator, with server persistence. It preserves tickets, messages and knowledge. Search includes hidden tickets; a new employee message returns its ticket to the queue. The destructive reset endpoint is retired. Operator transcript controls read “Раскрыть диалог” and “Свернуть диалог”, with heading “Тикет #ID”. The header omits the redundant website channel badge while retaining API status and other channel indicators. Existing responsive breakpoints and colors remain unchanged.

Operator ticket editor: department and priority selectors appear immediately below ticket identity. The reply composer is always visible near the bottom of the expanded ticket, with a bounded, vertically resizable textarea and internal scrolling. Work starts on composer focus; there is no separate start-work button. Mobile stacks assignment selectors using the existing 600px breakpoint.

Ticket pages: /tickets/{id} serves the application shell and loads the ticket through the existing authorized detail/messages APIs. Queue and personal-history titles are native links; primary activation navigates to the dedicated page. Restore direct links after authentication, support reload and browser Back/Forward, and clear routed content on session changes. The title includes ID and subject; transcript messages alternate alignment in the existing palette, with a single reply composer per role. Employee history sits below the intake grid as full-width compact rows.

Reply and closure refinement: the knowledge category precedes the reply textarea; the single send button reads 'Отправить' and sits below the field. Close buttons use text #323940 on #EAA5A5. Closing opens a native auto popover with an explicit reason and confirmation; outside click and Escape cancel/reset the pending choice. Native selects retain native cancellation; settings dialogs also close on backdrop clicks. Reasons are recorded atomically with closure in tenant-scoped audit events and aggregated once per currently closed ticket, using the latest reason; historical closures appear as unspecified. Analytics displays this breakdown. No new responsive breakpoint is introduced.

Closure state fix: explicit operator closure events prevent delivery retries from downgrading a closed ticket to resolved. Ticket detail returns the latest closure reason; show it beside the disabled closed control, hide the reply composer for closed/auto-resolved tickets, and retain the closed row label after navigation and reload.

Queue lifecycle: show only New, In progress and Closed in the status filter. Server display_status classifies closed/auto_resolved as closed, prior operator work sessions/messages/replies as in progress, and remaining routed/automated intake as new. Apply the status filter before pagination, using the same classification for row labels. Requester_email resolves the ticket's stored member ownership within its tenant; show linked profile email instead of Telegram/MAX sender identity, while preserving the original sender for delivery. Unlinked bot tickets display 'Почта не привязана'. Search also includes the linked email.

Queue header refinement: 'Обращения' and the live result count sit directly beneath 'Очередь обращений'. Search, department, status and priority share one filter panel, with actions beneath. Use four columns above 1250px, two columns through 1250px, and one column at the existing 600px mobile breakpoint to preserve usable controls.

Settings navigation: consolidate knowledge, integration tools and service configuration under a native expandable Settings group. Provide separate items for knowledge, channels, departments/communication, import, answer preview, website widget, API keys and API testing. Builder panels render one subsection at a time; preserve unsaved form values when switching between builder subsections. Existing role permissions control each child and hide the group for roles without settings access. Outside click/Escape dismiss the group. The existing 850px navigation breakpoint gives the expanded group a full-width row and a two-column submenu on mobile.
